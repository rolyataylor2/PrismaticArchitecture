# ADR 0149: Selected corrections to an execution remainder

Status: Accepted implementation target; runtime implementation remains unfinished.
Date: 2026-10-08
Source: Researcher clarification: cognition can correct a skill at an intermediate step, regenerate the remaining task and retain the instruction in a reusable revision.
Extends ADRs 0142, 0144, 0146 and 0147.

## Correction boundary

A running selected strategy has an immutable original contract and an operational ledger. A correction changes future authorized operations through a newly selected contract; it never rewrites the original action, tool arguments, already submitted operations or outcomes. Steps already completed remain accounted for. Their prior tool calls must not be replayed simply because a revised strategy resembles the original skill.

Before submitting a subsequent native step, an opt-in correction-capable worker can await the completion of a checkpoint assessment/review already issued for its preceding result. Background monitoring alone remains nonblocking. The boundary must be cancellable independently of inference: selected pause may cancel the worker while Self's review waits for confirmed local cessation. A worker awaiting that same review without an abort path would deadlock. No inference lock can become authority to submit tools or suppress a hard stop. Deadlines continue to run while cognition considers a correction.

The host records the actual boundary reached, completed/submitted step references and any unresolved submission. A proposed correction refers to this bounded activity context. Selection is insufficient unless the host independently validates same Agent/thread, original selected activity, current boundary, once-only consumption, captured remaining budgets and current permission. A stale correction must be rejected or reconsidered against a new checkpoint; it cannot silently insert itself at a later step. Unknown external effects block automatic resumption until new factual evidence resolves them. Local cancellation alone does not resolve those effects.

## Remainder handoff

Self chooses the correction from ordinary Parts' expressed proposals. The host preserves the original criterion/constraints unless Self explicitly selects a changed intention through the defined replacement path. The successor records the original contract, checkpoint, correction bid/reason and only its newly selected remaining strategy. Submitted step counts and duration cannot reset through repeated corrections. Changes in permission or late-bound preferences are checked again. A separately selected final verification may verify the whole intended result; tool success or cessation alone cannot do so.

Self remains world-blind. It receives expressed arguments and narrow mediated activity context, not raw tool results, operation ledgers or WorldState. Checkpoint/world observations enter ordinary Parts through one immutable snapshot. Runtime validates operational references rather than generating psychological meaning or deciding that a correction is beneficial.

## Learning and inspection

The ended chain preserves the original selected skill/version, completed prefix, every selected correction, rejected/stale corrections, expressed thoughts, activation context, successor contracts and actual outcomes. Conditional consolidation can propose a new skill version from this chain. It infers when the correction applies; an ordinal instruction such as “insert at step four” is not sufficient evidence of reusable applicability. A revised full procedure may include the original prefix for future fresh tasks, but must never be used to replay that prefix within the current execution.

Candidate formation and adoption remain separate. A correction used once is not automatically established knowledge. Preserve failed corrections and uncertain causal attribution. Inspection must distinguish the revised remainder used this time from the full procedure proposed for future use, with source bids and reasons for each change.

## Required verification

Exercise ordinary cognitive correction between completed tool calls, exact prefix preservation with no replay, stale boundary rejection, cancellation while inference is pending without deadlock, cumulative budgets, permission changes, unresolved-response refusal, thoughts-only/continued activity, final whole-goal verification, restart without worker replay and candidate skill revision with full chain provenance. Add sourced normal-pipeline Simulation Tests with an uncovered condition and a comparison that reuses the revised skill on a fresh task. Deterministic fixtures validate control flow only.

This decision does not claim that post-effect revision/resume is implemented. Existing selected pause, no-submission guidance continuation and conditional consolidation remain compatibility foundations.

The initial implementation adds the optional `awaitCheckpointReview` control and a native background boundary after a successful result and before the next step. The host waits for issued Agent inference; cancellation/deadlines release the wait independently, preserving prior call traces. It does not yet record a selectable remainder boundary, accept a correction strategy, or resume submitted work. These remain required work above.

The host now appends `execution.checkpoint_boundary` with the live owned execution/contract, completed call count and successful trace references checked against the stored ledger. This is a historical reached-boundary record, not proof the worker remains suspended and not a selectable correction token. Any future correction consumption must revalidate current ownership, submissions and boundary freshness. Duration expiry during a never-settling review stops before another submission.

The wait references the review issued for that exact completed trace, not every later inference request for the Agent. Ordinary per-Agent inference serialization is retained; later unrelated work does not become a reason to drain the whole queue before continuing. Review infrastructure failure blocks at the boundary and remains separately recorded. Terminal execution clears the temporary host review handle.

Tool-result checkpoints supply Parts with a factual completed-call count and a bounded ordered tool-name summary from the matching contract's successful ledger responses. This contains no arguments, raw results or private state. It is frozen historical progress at that result, not proof of current boundary freshness or whole-goal completion. Self's mediated activity interface is unchanged; Parts may express relevant observations through their ordinary products.

The initial correction-boundary validator checks latest reached-record identity, live local ownership, same selected Agent/thread contract, exact prefix tool arguments, distinct matching successful responses, chronology, remaining step budget and absence of additional submissions. Native waiting invokes it before and after review. This independently checks operational evidence but does not select or consume a correction, suspend through a replacement handoff, or issue successor authority.

The validator also accepts the opaque tool-result reference supplied in ordinary checkpoint facts, resolving it only against the latest reached boundary's final successful trace. Conflicting boundary/checkpoint references are rejected. Source ownership and event attribution are checked explicitly. An expired original contract cannot admit correction, and the result exposes its original absolute deadline and remaining duration/steps for a future cumulative-budget handoff. This does not introduce a proposal field or bypass selected-contract admission.

Live boundary admission additionally requires the owning local worker to report its exact completed-step wait. The native executor enters that state immediately before invoking the host checkpoint callback and clears it in a finally block after review, failure, cancellation or deadline. A persisted reached record and live worker ownership alone cannot prove suspension. This local state is ephemeral operational evidence, not durable restart authority, a correction receipt or a source of cognitive meaning. Selected remainder consumption/handoff remains required.

Remainder preparation independently checks the correcting cycle's recorded selected bid, chronological same-Agent/thread relationship, exact live boundary and current tool grants. It preserves the original selected goal and success-criterion text and all original constraints, while allowing additional constraints and a newly selected whole-result verification. The explicit remainder must fit the smaller of the remaining original and current profile limits; it captures the original absolute deadline. Preparation yields immutable operational data only, not a persisted contract, consumption receipt or dispatch permission. Atomic consumption, successor compilation/dispatch and repeated-chain reconciliation remain required before runtime adoption.

An explicit remainder may consist solely of a selected whole-result verification call when prior work needs no further mutation. Native execution treats that as an executable strategy, not a missing-instruction request. Only absence of both steps and a verifier requires guidance. Verification remains a granted, budgeted external operation and its failure cannot establish completion.

Ordinary operational proposals can explicitly identify a remainder correction by target execution and opaque checkpoint-result reference. This one-time relationship must be exclusive of pause, guidance, teaching and retained-method invocation bindings, and must be stripped from reusable procedures. Until durable consumption and successor dispatch are implemented, selection records a rejected correction contract with zero tools; a candidate remainder must never accidentally execute as an independent activity. Application admission runs the live preparation gate to retain a specific rejection reason, but successful preparation does not overcome the unavailable handoff. Replacement adapters and storage must independently enforce rejected contracts. Factory prompts describe this availability accurately rather than promising correction execution.

Accepted remainder contracts capture parent execution/contract, exact settled prefix references, checkpoint result, original absolute deadline and remaining captured limits. A host-owned preparation callback may supply this data; a proposal alone cannot. Before any handoff, a synchronous transaction rechecks the exact live preparation and records one immutable consumption claim. A claim is not confirmation of cessation or tool authority: successor gateway access must remain refused until a separately verified ready handoff records the preserved parent transition. Replayed claims, mismatched lineage and rejected contracts cannot consume a checkpoint. Initial claim support does not itself implement worker replacement or successor dispatch.

Consumption must account for host tool reservations as well as actual submissions. A pending or additional reservation prevents capture even before MCP submission; reservations, when present, must match the settled prefix and end before the boundary. An original gateway rechecks current authority after asynchronous connection refresh. Thus a connection wait cannot carry previously checked authorization across a consumed checkpoint.

Ready handoff requires a recorded blocked parent whose attempts and successful settled ledger exactly equal the captured prefix, without extra or pending authorizations. The host records a separate ready receipt and transitions that same immutable parent to continued by the selected successor contract in one transaction. This transition cannot declare whole-goal completion, undo effects or erase the stopped segment. Gateways and storage independently verify receipt, parent/contract selection, thread, constraints, exact prefix and remaining limits. Only this supported recorded transition may move a blocked parent to continued. Runtime dispatch remains separate from readiness evidence.

A ready receipt does not establish successor completion. Storage independently checks the successor's exact tool ledger and final selected verification criterion before accepting completed status. A verification-only remainder may pass that evidence check without prior successor mutation steps.

The external handoff coordinator consumes the selected correction before requesting local cancellation, awaits the owning worker's persisted settlement under both original and selected deadlines, then records readiness transactionally. Failure preserves whether consumption committed; it cannot silently retry, fabricate cessation or restore original gateway authority. An expired or unrecordable stop remains unready. This coordinator returns operational readiness only, not whole-goal success, and never chooses a new goal or procedure. Automatic cognitive successor dispatch is a separate integration step.

Native integration now admits host-prepared Self-selected remainder authority through the ordinary pipeline. Dispatch first invokes the external handoff coordinator; only a confirmed ready handoff may schedule a fresh worker for the selected remainder. Ready dispatch bypasses coordination rather than re-consuming the same checkpoint, while gateways independently verify readiness. Background startup occurs after the new running handoff is persisted. The successor uses the captured remaining limits and absolute original deadline. A failure returns a zero-submission blocked successor and preserves the consumed parent history. Current tool-result checkpoint references may appear in contextual Part proposal schemas; Self still receives only expressed proposals and mediated activity, never raw ledger or WorldState.
