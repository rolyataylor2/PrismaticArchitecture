# ADR 0150: Agent Skills packages and official MCP infrastructure

Status: Accepted implementation target; Agent Skills package storage remains unfinished.
Date: 2026-10-08
Source: Researcher instruction to store skills in the Agent Skills open format and use the official MCP client SDK.
Extends ADRs 0140, 0143, 0144, 0147 and 0148.

## Portable procedural knowledge

Use the [Agent Skills specification](https://agentskills.io/specification) for stored portable skill packages. Each package has a directory whose name matches the frontmatter name, a required `SKILL.md` with YAML `name` and `description`, and Markdown instructions. Optional `references/`, `assets/` and `scripts/` resources use relative package paths. Preserve specification naming/length constraints and validate packages. Display names and internal continuity IDs remain distinct from the portable directory name; conversion must not destructively rename living records or lose version history.

Readable procedures describe applicability, conditional branches, current-preference revalidation, verification and escalation. Supporting references preserve skill versions/variants, actual source bids and expressed thoughts/reasons, accepted and rejected corrections, activation context, evidence, maturity assessments and limitations. Keep bulky provenance outside the main instruction body for progressive disclosure. Include explicit compatibility requirements for exact tool bindings; portable format compliance does not prove operational portability or parameterized transfer.

Format support must include real stored/versioned packages and a defined load/import/export path, not merely an optional Markdown rendering of a proprietary record. SQLite may retain indexed views, immutable development/approval history and host administration, but the package's procedural contents must have a single defined authority with content/version reconciliation. Preserve original legacy records; conversion creates attributable package versions. Storage location is configurable and cannot assume the repository workspace. External edits/imports become validated proposed revisions rather than silent replacements of approved procedures. Atomic persistence/recovery must prevent package and registry divergence.

Package metadata or `allowed-tools` cannot confer host grants, Self selection, execution approval or established maturity. Importing scripts does not execute them. Agent isolation, scope, current permissions, late-bound preferences and immutable selected-contract checks remain enforced by the host. Standard-format knowledge and host-specific executable method bindings must have an explicit relationship; arbitrary instructions must not be represented as a validated exact operation merely because they parse as Markdown.

## Official MCP client

Use the [official TypeScript MCP SDK](https://github.com/modelcontextprotocol/typescript-sdk) for protocol client and transport. The current manager imports `Client` and Streamable HTTP from `@modelcontextprotocol/client`, stdio from its `/stdio` entry point and the SDK AJV validator. Root dependencies currently use the official v2 packages. Retain framework-owned grants, argument/result validation, scoped submission ledgers, deadlines and ambiguous-outcome handling around this client; those are Agent host responsibilities, not a parallel protocol implementation.

## Required verification

Verify standard frontmatter/naming and package/resource validation; immutable exact/conditional round trips; preservation of bids/thoughts/reasons and failed evidence; real persistence/restart and content reconciliation; safe explicit import without automatic execution/approval; Agent/scope isolation; legacy continuity; and retained official SDK transport tests. Review factory skill context and loading prompts when package loading responsibilities change. A generated compliant file alone does not establish completion of stored-package support.

## Initial package snapshot implementation

The core builder generates compliant name/description frontmatter and Markdown with relative method/development references. The SDK can atomically persist immutable content-addressed directory snapshots under configurable `ONTOAGENTIC_SKILLS_ROOT`; GET/POST `executive-skills/:id/package` builds/stores an explicit current snapshot. The method asset preserves exact host-specific state and the development reference includes versions, source expressions, bids, activation, checkpoint reviews, outcomes and related variants. Conditional packages bundle each exact preserved member as a relative branch asset, with its criterion and source bid/thought evidence. Missing, conditional, foreign or incompatible scoped members reject before persistence. Repeated persistence verifies existing contents instead of rewriting them. No inference or approval mutation occurs. These are stored portable snapshots: canonical package loading/edit/import reconciliation, progressive runtime loading and reference-validator integration remain unfinished; automatic lifecycle mirroring is described below. SQLite is still the current runtime instruction authority.

Stored snapshot loading is implemented through `AgentSkillPackages.load` and GET `executive-skill-packages/:digest`. It reconstructs and checks the immutable content digest, exact branch dependencies and resource contents, rejecting external edits, extra files and nonregular resources. Repeat persistence uses the same integrity check. Loading does not adopt or approve package instructions; generic imports and canonical runtime reconciliation remain pending.

Historical package export preserves exact immutable procedure versions. POST `executive-skills/:id/package` accepts an optional positive `version`; POST `executive-skills/:id/package-history` snapshots every preserved version, including rejected and superseded records. All packages are built synchronously before persistence begins, so a concurrent revision cannot mix registry views between files. Development references explicitly distinguish the historical procedure from audit evidence available at export time, which may include later outcomes. Partial filesystem failures retain completed immutable snapshots and permit retry; this operation does not claim atomic adoption or a canonical registry migration.

Application-owned `ExecutiveSkills` now schedules standard package persistence for every SDK lifecycle write (proposal, conditional formation, validation, revision, approval/rejection/archive, maturity and rollback). Because transactions are synchronous, the queued job rechecks the exact preserved version after the current call stack before exporting; enclosing transaction rollback publishes no package. Pending writes are tracked and `Application.close` drains them before closing connections. `AgentSkillPackages.flush` reports failed filesystem writes separately from committed registry state; explicit persistence/history export can retry. Direct storage writes and standalone SDK instances without the callback require explicit reconciliation. This is an automatic package mirror, not canonical package authority, generic import or an atomic filesystem/SQLite adoption protocol. No provider prompts or cognitive access boundaries change.

`AgentSkillPackages.reconcile` and POST `executive-skill-packages` backfill one Agent’s complete preserved skill history, including direct-storage/legacy versions. All packages are captured before the first filesystem write; immutable partial output can be retried. Reconciliation supplies no authority, approval, inference or tool execution, and does not adopt external edits.

The development command `npm run validate:skills -- <skill-directory> ...` runs the official `skills-ref validate` executable, with explicit failure for missing tools, validation errors and timeouts. `SKILLS_REF_BIN` supports isolated/pinned installations. This is supplementary format verification; the demonstration reference library does not become production inference or execution infrastructure. Host digest, exact method and authority checks remain independent.

Reference validation was run against all 129 currently stored generated packages (23 conditional) with official revision `69ef37e9424c0a7ea9dd2293b559e43ec8176379`; all passed. Its parser coerces metadata values to strings, so the development command additionally inspects original YAML nodes to enforce string keys/values, rejecting nested and numeric metadata. Runnable positive/negative controls require a functioning official validator. Preserved evidence is `docs/development/observations/agent-skills-reference-2026-10-08.json`; format validation does not validate host binding semantics, authority or cognition.

`parseAgentSkillPackage` validates standard YAML frontmatter, directory-name agreement and relative resource paths while preserving generic Markdown/resources. Original YAML metadata must contain string scalar keys/values; nested and numeric values reject without coercion. Generated snapshots use this parser before storage. POST `executive-skill-packages/preview` provides a same-Agent read-only format preview of supplied `{name, files}`; no files, proposals, grants, execution or cognitive state are changed. This supports generic intake validation but does not yet persist imported proposals or adopt instructions as executable methods. `yaml` is now a runtime format dependency; the official demonstration validator remains development-only.

Generic imports are external portable-knowledge proposals, not exact executable `ExecutiveSkill` records. Store an immutable proposal manifest beside an unchanged standard package under the configurable skill root, scoped to the importing Agent. Preserve declared source/reason and explicit prior-proposal lineage; a revised package creates another proposal. Content identity covers both package digest and attribution. Validate and publish atomically; inspect/reload verifies identity and resources. No import status grants host permission or adopts foreign bindings. The later bridge to selected executable methods and canonical runtime loading remains required.

Generic text-package proposal persistence is implemented by `AgentSkillImports`. POST `executive-skill-imports` accepts `{name, files, source, reason, previousId?}`; GET lists proposals or loads an ID. Packages retain unchanged standard files under `ONTOAGENTIC_SKILLS_ROOT/imports`, with an immutable sibling manifest. Identity covers package content and declared attribution; explicit previous-proposal links must resolve within the same Agent. Atomic rename publishes a complete proposal, repeat import verifies existing bytes, and loading rejects changed contents or nonregular resources. Source-host active metadata and `allowed-tools` remain inert. No exact skill registry, host grant, cognitive state or operation is created. Binary resource intake, proposal review/adoption into selected executable methods, UI inspection and canonical runtime loading remain required.

Import knowledge review is a researcher administration decision (`reviewed` or `rejected`) with a reason, optimistic revision and immutable history stored separately from unchanged package bytes. It must neither activate an exact method nor confer grants, maturity or Self selection. Revision races have one winner, and inspection preserves previous decisions. Executable adoption still requires the selected-method/evidence bridge.

Canonical migration begins with an immutable package binding for each exact Agent/skill/version. The first stored snapshot binds that version; later audit-enriched exports remain separate snapshots and cannot retarget the binding. Binding resolution loads and verifies the package, Agent, continuity ID and preserved method version. SQLite continues to administer authority/history during this migration; package resolution alone does not finish runtime adoption. Binding publication is atomic, conflicts verify exact method equivalence, and backfill uses explicit reconciliation.

Generated package persistence now publishes an immutable Agent/skill/version binding through an exclusive atomic filesystem link. The first package snapshot remains bound; later audit-enriched exports cannot retarget it and must preserve the exact method. `resolveMethod` and GET `executive-skills/:id/package-method/:version` load that package and verify content, ownership and continuity/version attribution, including exact conditional members. Explicit history reconciliation backfills bindings. Runtime selection/execution still uses SQLite and has not yet switched to this resolver; the binding layer is migration groundwork, not completed canonical package authority.

Application-backed fresh skill selection must load the immutable parent/member package before compiling the execution contract. The core accepts an external package resolver, preserving filesystem separation. Compare loaded records with current immutable host registry approval/scope state and recheck selection after asynchronous loading. Capture the procedure from the verified package, not a silently substituted registry fallback. Missing/corrupt/unbound packages reject fresh invocation before submission; explicit reconciliation is required for legacy versions. Already-selected frozen contracts remain independently verifiable against preserved host history. Generic import adoption and progressive instruction context remain separate requirements.

Application-backed fresh exact/conditional invocation now resolves the stored immutable package before contract compilation, captures its procedure and rejects missing/corrupt/unbound or registry-inconsistent packages. Current approval, scope, limits and grants are independently rechecked after asynchronous loading; no registry fallback replaces failed package resolution. The core receives an optional external resolver and does not own filesystem access. Pending package writes/failures are scoped to the requesting Agent; shutdown still drains all. Already-selected frozen contracts retain their existing verification path. Generic imported knowledge adoption, progressive instruction loading and broader canonical migration remain unfinished.

Fresh Application-selected method contracts now capture the immutable parent package digest and, for conditional invocation, the selected member package digest. Host package metadata remains separate from the ordinary selection reference comparison, so unchanged selected authority is rechecked after asynchronous loading. Inspection projects these digests under Stored package provenance. Legacy contracts without digests remain readable without fabricated provenance. No new inference task or raw package context is supplied to Self.

Explicit message intake may request up to ten same-Agent reviewed import IDs. Before cognition, resolve immutable main instruction text, package digest and exact review revision into attributed external procedural metadata in the shared WorldState. Exclude supporting audit/resources and source-host authority. Every activated Part receives the same snapshot; Self receives only expressed Part products, and factual evidence contexts used to evaluate predictions omit procedural metadata. Rejected/unreviewed/missing imports reject before inference. Intake does not itself select a method, invoke scripts or retain a skill. Automatic document discovery, model-requested progressive retrieval and explicit adoption lineage remain required.

## Cross-Agent package proposals

A researcher may explicitly copy an inspected immutable skill version into another Agent's portable-knowledge proposals. Resolve and verify the original binding, preserve unchanged standard files and development references, and record source Agent/skill/version/digest and target proposal lineage. Source approval, maturity, private memory, credentials and tool grants do not become target executable authority. Existing generic review and explicitly selected document intake govern subsequent consideration; executable adoption still requires the target's own selected instructions, evidence and permission checks. Repeat copies of identical attribution/content retain target review history. This does not add a global skill owner or shared psychological state.
